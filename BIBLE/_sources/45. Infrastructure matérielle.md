# 47. Simulation Headless

Le serveur doit pouvoir fonctionner **sans interface graphique**.

Exemple :

```text
genesis-server
```

Le serveur continue de simuler le monde même lorsqu'aucun joueur n'est connecté.

Godot peut être lancé uniquement lorsque le joueur souhaite observer le monde.

Cela permet :

- fonctionnement 24/7 ;
- faible consommation de ressources ;
- redémarrage automatique ;
- simulation sur serveur ;
- plusieurs clients potentiels ;
- sauvegardes indépendantes du rendu.

# 49. Utilisation du CPU

Le CPU constitue la ressource principale de la simulation.

Il devra être utilisé pour :

- simulation du monde ;
- évolution ;
- comportement des agents ;
- économie ;
- politique ;
- génération d'événements ;
- pathfinding ;
- calculs statistiques ;
- traitement de la mémoire ;
- préparation des appels IA.

Les systèmes doivent être conçus pour fonctionner en parallèle lorsque cela est pertinent.

---

# 50. Utilisation de la RAM

Les 32 Go de RAM permettent de conserver une quantité importante d'état en mémoire.

Le principe recherché :

```text
RAM
│
├── monde actif
├── agents actifs
├── villes
├── relations
├── connaissances
├── événements récents
└── cache
        │
        ▼
      DISQUE
        │
        ├── historique
        ├── sauvegardes
        └── archives
```

Toutes les informations n'ont pas besoin d'être constamment chargées en mémoire.

---

# 51. Stockage

Le disque actuel de 1 To est suffisant pour le prototype.

Cependant, le stockage sera rapidement important si le projet conserve :

- historique complet ;
- souvenirs ;
- journaux ;
- conversations ;
- événements ;
- sauvegardes ;
- états successifs du monde.

### Priorité matérielle future

**Ajouter un SSD** avant d'augmenter significativement la complexité du stockage.

Le HDD peut rester utilisé pour :

- archives ;
- sauvegardes ;
- snapshots ;
- anciens mondes.

Le SSD sera préférable pour :

- base de données active ;
- fichiers de simulation ;
- logs ;
- cache ;
- données fréquemment consultées.

---

# 52. GPU

La Radeon RX 470/480 n'est pas considérée comme une dépendance fondamentale du moteur.

Le projet doit fonctionner même sans accélération GPU spécifique.

Le GPU pourra être utilisé pour :

- rendu Godot ;
- effets visuels ;
- visualisation de grandes populations ;
- expérimentations de calcul parallèle ;
- éventuelles charges IA compatibles avec l'environnement logiciel.

L'architecture ne doit cependant pas supposer qu'une charge IA donnée pourra être accélérée efficacement sur cette carte.

# 53. Stratégie de performance

Le nombre d'individus ne doit pas déterminer directement le nombre de calculs complexes.

Exemple :

```text
1 000 000 organismes
        │
        ├── 950 000 agents simplifiés
        │
        ├── 49 000 agents intermédiaires
        │
        └── 1 000 agents détaillés
```

Seuls certains individus nécessitent une simulation cognitive détaillée.

```text

```

# 55. Le LLM ne doit pas simuler le monde

Principe architectural critique :

> **Le LLM raconte ce que pense l'entité. Il ne décide pas des lois du monde.**

Le moteur reste l'autorité.

Exemple :

```text
SIMULATION

Une guerre commence.

        ↓

MOTEUR

Population : -4%
Production : -12%
Frontière déplacée
Ville détruite

        ↓

COGNITION

Agent important informé

        ↓

LLM

"Notre peuple est en train de perdre..."
```

Le LLM ne peut pas répondre :

> "J'ai décidé que nous avions gagné."

Le moteur détermine le résultat.

# 56. Système de tick

La simulation fonctionne avec un système de ticks.

```text
TICK
 │
 ├── environnement
 ├── ressources
 ├── organismes
 ├── besoins
 ├── mouvements
 ├── interactions
 ├── reproduction
 ├── société
 ├── économie
 ├── politique
 ├── technologie
 └── événements
```

Tous les systèmes n'ont pas besoin d'être exécutés à chaque tick.

Exemple :

```text
PHYSIQUE
→ chaque tick

BESOINS
→ chaque tick

ÉCONOMIE
→ toutes les X secondes

POLITIQUE
→ événementielle

TECHNOLOGIE
→ événementielle

COGNITION
→ à la demande
```

# 57. Événementiel plutôt que simulation permanente

Une grande partie du monde peut fonctionner selon un système événementiel.

Exemple :

```text
Agent
 ↓
a faim

EVENT : HUNGER

 ↓

Recherche nourriture

 ↓

EVENT : FOOD_FOUND

 ↓

Interaction

 ↓

EVENT : SOCIAL_INTERACTION
```

Cela permet d'éviter de recalculer inutilement des systèmes qui n'ont rien changé.

# 59. Philosophie de développement

Le projet doit rester expérimental.

Chaque couche doit être testable indépendamment.

Avant :

```text
vie
→ intelligence
→ civilisation
```

On doit pouvoir tester :

```text
100 organismes
↓
1000 générations
↓
observer l'évolution
```

Puis :

```text
100 individus intelligents
↓
simulation sociale
```

Puis :

```text
10 000 individus
↓
village
```

Et seulement ensuite :

```text
civilisation
```

# 60. Premier objectif technique

Le premier objectif n'est **pas** de créer une civilisation.

Le premier objectif est beaucoup plus simple :

> **Faire naître deux entités dans un environnement et les regarder évoluer sans intervention du joueur.**

Prototype :

```text
MONDE
 │
 ├── énergie
 ├── ressources
 └── espace
       │
       ▼
   ENTITÉ A
       +
   ENTITÉ B
       │
       ▼
   interaction
       │
       ▼
   adaptation
       │
       ▼
   reproduction
       │
       ▼
   mutation
       │
       ▼
   évolution
```

Si cette boucle est amusante à observer...

**Genesis fonctionne déjà.**

Tout le reste pourra ensuite être construit au-dessus.

# 69. Vision finale

Genesis ne doit pas être un jeu dans lequel le joueur suit une histoire.

Il doit être un jeu dans lequel **le joueur crée les conditions permettant à une histoire d'exister**.

Le joueur peut être :

```text
observateur
scientifique
protecteur
manipulateur
créateur
destructeur
prophète
dieu
```

Mais le monde reste libre.

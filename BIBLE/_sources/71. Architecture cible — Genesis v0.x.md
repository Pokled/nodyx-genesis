# 71. Architecture cible — Genesis v0.x

## 71.1 Plateforme de référence

La première version de Genesis est développée et optimisée pour le serveur domestique actuel.

### Configuration de référence

```text
CPU
Intel Xeon E5-2680 v4
14 cœurs / 28 threads
2.40 GHz → 3.30 GHz
AVX2 / FMA
35 Mo L3

RAM
32 Go DDR4

GPU
AMD Radeon RX 470/480

STOCKAGE
~932 Go HDD
~796 Go disponibles

SWAP
~32 Go

OS
Linux

NUMA
1 nœud
```

Cette machine constitue la **plateforme Genesis de référence**.

---

# 72. Philosophie matérielle

Genesis doit être capable de fonctionner entièrement sur une seule machine.

```text
┌─────────────────────────────────────┐
│             SERVEUR                 │
│                                     │
│  ┌─────────────┐  ┌─────────────┐  │
│  │ Simulation  │  │     API     │  │
│  └─────────────┘  └─────────────┘  │
│                                     │
│  ┌─────────────┐  ┌─────────────┐  │
│  │  Database   │  │     AI      │  │
│  └─────────────┘  └─────────────┘  │
│                                     │
└──────────────────┬──────────────────┘
                   │
                réseau
                   │
                   ▼
          ┌─────────────────┐
          │     GODOT       │
          │     CLIENT      │
          └─────────────────┘
```

La distribution sur plusieurs machines est une possibilité future et non une dépendance.

---

# 73. Budget de ressources

Le système doit conserver une marge importante pour Linux et les services du serveur.

Objectif initial :

```text
RAM
│
├── OS + services
├── Genesis Engine
├── Database
├── Cache
├── AI
└── marge de sécurité
```

Genesis ne doit pas chercher à consommer toute la mémoire disponible.

Une marge importante doit rester disponible afin d'éviter les situations d'OOM et permettre l'évolution progressive du projet.

---

# 74. CPU

Les 14 cœurs physiques constituent la ressource principale du moteur.

Le moteur devra favoriser :

- tâches parallèles ;
- batch processing ;
- simulation par lots ;
- files de tâches ;
- calculs vectorisables ;
- réduction des allocations ;
- traitement événementiel.

Le multithreading doit être introduit progressivement.

La priorité est d'obtenir :

> **un moteur correct et mesurable avant un moteur massivement parallèle.**

---

# 75. RAM

La RAM doit principalement contenir :

### Données chaudes

Informations nécessaires à la simulation immédiate :

- terrain actif ;
- ressources ;
- organismes actifs ;
- agents ;
- groupes ;
- événements récents ;
- cache.

### Données froides

Informations pouvant rester sur disque :

- historique ancien ;
- conversations anciennes ;
- souvenirs archivés ;
- snapshots ;
- statistiques historiques.

---

# 76. Stockage

Le disque actuel est suffisant pour Genesis v0.x.

Organisation prévue :

```text
/var/lib/genesis/
│
├── world/
│
├── database/
│
├── snapshots/
│
├── history/
│
├── logs/
│
├── cache/
│
└── backups/
```

Le projet ne doit pas remplir inutilement le disque.

Les historiques peuvent être compressés ou archivés.

---

# 77. Sauvegarde

La simulation étant persistante, les sauvegardes constituent une fonctionnalité fondamentale.

Genesis doit pouvoir créer :

```text
snapshot_000001
snapshot_000002
snapshot_000003
...
```

Un snapshot doit permettre de restaurer l'état du monde à un instant donné.

Objectif :

> **Une erreur de simulation ne doit jamais détruire l'univers.**

---

# 78. Snapshots et expérimentation

Les sauvegardes peuvent également servir d'expérimentation.

Exemple :

```text
WORLD A
│
├── aucune intervention
│
└── évolution naturelle

WORLD B
│
├── miracle au tick 100 000
│
└── observer les conséquences
```

Un même monde peut donc être cloné et soumis à différentes expériences.

---

# 79. Reproductibilité

La simulation doit utiliser une source d'aléatoire contrôlable.

Exemple :

```text
WORLD SEED

GENESIS-2026-001
```

Avec le même seed et les mêmes paramètres, le moteur doit idéalement pouvoir reproduire les mêmes événements déterministes.

Cela permettra :

- debugging ;
- tests ;
- comparaison d'expériences ;
- recherche de bugs ;
- expériences scientifiques.

---

# 80. Observabilité

Genesis doit toujours savoir ce qui se passe.

Le serveur devra produire :

```text
CPU
RAM
population
ticks/sec
simulation latency
events/sec
agents actifs
LLM calls
database latency
```

Ces informations seront accessibles depuis une interface de monitoring.

---

# 81. Priorité performance

Ordre de priorité :

```text
1. Correctness
2. Stability
3. Persistence
4. Observability
5. Performance
6. Scale
```

Il est inutile de simuler un million d'individus si deux individus produisent déjà des états incohérents.

---

# 82. Échelle visée

Genesis ne définit pas initialement un nombre maximal d'entités.

L'échelle sera déterminée expérimentalement.

Objectifs indicatifs :

```text
v0.1
2 → 100 organismes

v0.2
100 → 10 000 organismes

v0.3
10 000 → 100 000 organismes

v0.x
100 000+
```

Ces valeurs ne constituent pas des garanties.

Elles servent de jalons de performance.

---

# 83. Le véritable benchmark

Le benchmark principal ne sera pas :

> "Combien d'entités pouvons-nous afficher ?"

Mais :

> **"Combien d'entités pouvons-nous simuler correctement par seconde ?"**

Exemple :

```text
Population : 50 000

Simulation speed :
×1 réel
×10
×100
×1 000

CPU :
72 %

RAM :
11 Go

Tick :
4.2 ms
```

---

# 84. Godot

Godot est considéré comme le **client visuel**.

Il ne doit pas être nécessaire au fonctionnement du monde.

Si Godot est fermé :

```text
Genesis continue.
```

Si le serveur redémarre :

```text
Genesis recharge le dernier snapshot.
```

Si aucun joueur n'est connecté :

```text
Genesis continue.
```

---

# 85. Client / serveur

Communication initiale :

```text
GODOT
  │
  │ HTTP / WebSocket
  ▼
GENESIS API
```

Les données envoyées au client doivent être limitées à ce qui est nécessaire à l'affichage.

Le client ne reçoit pas nécessairement l'intégralité de la simulation.

---

# 86. Intérêt de cette architecture

Cette séparation permettra éventuellement de créer :

```text
CLIENT GODOT
        │
        ├── PC
        ├── Laptop
        └── autre machine
```

tout en gardant :

```text
        SERVEUR GENESIS
             │
             └── monde unique
```

Plusieurs clients pourraient donc observer le même univers.

---

# 87. Évolution future du matériel

Aucune mise à niveau matérielle n'est nécessaire pour Genesis 0.x.

Éventuellement :

### Priorité 1

SSD pour remplacer ou compléter le HDD.

### Priorité 2

RAM supplémentaire si les simulations deviennent massives.

### Priorité 3

GPU plus puissant si les besoins graphiques ou IA le justifient.

### Priorité 4

Deuxième machine si le moteur atteint les limites du serveur.

Le projet ne doit jamais nécessiter ces évolutions pour son fonctionnement initial.

---

# 88. Principe architectural

> **Commencer avec une machine.**
>
> **Construire comme si elle était infinie.**
>
> **Mesurer ses limites.**
>
> **Optimiser avant d'acheter du matériel.**
